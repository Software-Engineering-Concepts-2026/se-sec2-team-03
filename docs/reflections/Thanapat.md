1."จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"

ในโปรเจกต์ที่ผ่านมา ผมเคยปล่อยให้มีโค้ดที่ซ้ำซ้อนและไม่ได้จัดระเบียบ เพราะคิดว่ายังใช้งานได้อยู่ ผลคือเมื่อโปรเจกต์ใหญ่ขึ้น โค้ดอ่านยาก แก้ไขลำบาก และเกิด Bug ได้ง่ายขึ้น ทำให้เสียเวลาในการพัฒนาในระยะยาว

2."อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"

สำหรับผม Take Responsibility คือการรับผิดชอบต่องานและหาทางแก้ปัญหาแทนการโทษปัจจัยอื่น ตัวอย่างเช่น หากทำงานไม่ทันเพราะติดปัญหา API ผมจะไม่บอกแค่ว่า "ทำต่อไม่ได้" แต่จะเสนอทางเลือก เช่น ใช้ Mock Data ไปก่อน หรือขอความช่วยเหลือจากทีม Backend เพื่อให้งานเดินหน้าต่อได้
