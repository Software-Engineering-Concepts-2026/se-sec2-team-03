1."จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"
  -ในโปรเจกต์ที่ผ่านมา "หน้าต่างบานแรกที่แตก" คือการละเลยเรื่อง Hard-coded การตั้งค่าระบบและฐานข้อมูลไว้ชั่วคราว รวมถึงการยอมให้มี Logic ที่ซ้ำซ้อนในโมเดลการประมวลผล (เช่น YOLO หรือ OpenCV) เพียงเพื่อต้องการให้ส่งเดโมได้เร็วขึ้น
ผลกระทบระยะยาว: เมื่อปล่อยปละละเลย ความมักง่ายนี้จะกลายเป็นตัวอย่างให้โค้ดส่วนอื่น ๆ ถูกเขียนอย่างไม่เป็นระเบียบตามไปด้วย เกิดเป็น Technical Debt ก้อนโต จนทำให้ฟังก์ชันเหล่านั้นกลายเป็น "God Function" ที่ยาวและซับซ้อน ส่งผลให้คนในทีมกลัวและไม่กล้าทำ Refactoring เพราะกังวลว่าระบบภาพรวมจะพังครับ

2."อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้" ขอคำตอบสั้นๆ
  -Take Responsibility: คือการแสดงความเป็นเจ้าของ (Ownership) ต่อผลลัพธ์ของงาน ไม่ปัดความผิดให้ข้อจำกัดอื่น และมุ่งไปที่การหาทางออกเพื่อให้โปรเจกต์เดินหน้าต่อได้
ตัวอย่างการนำไปใช้ (Provide Options, Don't Make Lame Excuses):
หากระบบประมวลผลวิดีโอทำงานช้าจนทำให้หน้าเว็บค้าง แทนที่จะแก้ตัวว่า "เป็นเพราะสเปกเครื่องคอมพิวเตอร์ไม่แรงพอ" จะเปลี่ยนเป็นการเสนอทางเลือกให้ทีมตัดสินใจร่วมกันแทน:
"ทุกคนครับ ระบบประมวลผลไฟล์ขนาดใหญ่ยังมีปัญหาทำให้หน้าเว็บค้าง ผมต้องขออภัยด้วยครับ แต่เพื่อไม่ให้งานภาพรวมเลท ผมเสนอ 3 ทางเลือกครับ: 1) จำกัดขนาดไฟล์อัปโหลดเฉพาะหน้าเดโมนี้ก่อน 2) ปรับโค้ดไปใช้ระบบคิว (Background Task) แยกฝั่งประมวลผล หรือ 3) เปลี่ยนไปใช้โมเดลตัวที่เล็กลงเพื่อลดภาระเครื่อง เบื้องต้นผมกำลังลองทำทางเลือกแรกเพื่อให้พรุ่งนี้มีของส่งเดโมก่อน ทุกคนคิดเห็นอย่างไรบ้างครับ?"
