1. "จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"

= ในเชิงซอฟต์แวร์ Software Entropy คือความจัดระเบียบที่ลดลงเรื่อย ๆ (ความยุ่งเหยิงที่เพิ่มขึ้น) ในระบบ และ Broken Window Theory บอกเราว่า หากมี "หน้าต่างแตก" (โค้ดที่แย่, บั๊กที่ถูกละเลย, หรือสถาปัตยกรรมที่พัง) เพียงบานเดียวในโปรเจกต์แล้วไม่มีใครซ่อม มันจะส่งสัญญาณบอกทีมว่า "ไม่มีใครสนใจโปรเจกต์นี้หรอก" แล้วหลังจากนั้น โค้ดส่วนอื่น ๆ ก็จะเริ่มพังตามอย่างรวดเร็ว


2. "อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"

= หลักการ Take Responsibility (การยอมรับผิดชอบ) ในมุมมองของนักพัฒนาไม่ใช่แค่การพูดคำว่า "ขอโทษครับผมทำพัง" แต่คือการตระหนักว่า เราเป็นเจ้าของผลงานและผลลัพธ์ของมัน ไม่ว่าระบบจะพังเพราะ API เพื่อนล่ม อินเทอร์เน็ตหลุด หรือเครื่องมือมีปัญหา ทันทีที่เราได้รับมอบหมายงานนั้นมา เรามีหน้าที่บริหารความเสี่ยงและทำให้มันสำเร็จ
